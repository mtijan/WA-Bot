5.1 Strategi Cabang Repositori (Git Flow) #

Pengelolaan kode menggunakan model Git Flow terstandar untuk menjamin isolasi pengembangan fitur baru dari cabang utama produksi yang stabil.

main Cabang produksi stabil. Hanya menerima penggabungan PR resmi dari develop pasca testing rilis sukses.
develop Cabang integrasi utama. Seluruh fitur baru dikumpulkan dan diuji bersama di lingkungan staging ini.
feat/* Cabang fitur modular. Dibuat lokal oleh developer untuk pengerjaan modul mandiri (ex: `feat/warmer-engine`).

5.2 Standarisasi Penulisan Kode (Coding Guidelines) #

Panduan gaya penulisan kode proyek untuk menjamin tingkat keterbacaan yang tinggi serta skalabilitas pengembangan tim.

Tabel 5.2 -- Pedoman Kualitas Penulisan Kode Sumber Proyek
Kategori StandardisasiKebijakan ProyekTujuan Teknis & Contoh Konkret

5.3 Skrip Peluncur Operasional Server #

Skrip peluncur terintegrasi memicu startup otomatis untuk runtime backend Node.js dan dev-server React Vite secara simultan dalam satu perintah eksekusi. Pada Windows, backend dijalankan lewat wrapper PowerShell agar credential admin bisa diisi saat startup lokal tanpa menyimpan password di frontend.

Windows Shell Launcher:

run.bat
@echo off REM ======================================================== REM WA-Bot Pro - Windows Automated Launcher REM ======================================================== echo [*] Mengaktifkan Server Backend (Node.js Express)... start "WA-Bot Backend" powershell -NoExit -ExecutionPolicy Bypass -File "%~dp0backend\scripts\start_with_admin_auth.ps1" timeout /t 3 /nobreak >nul echo [*] Mengaktifkan Server Frontend (React Vite)... start "WA-Bot Frontend" /D "%~dp0frontend" cmd /k "npm run dev" echo [SUCCESS] Kedua server berhasil diaktifkan di jendela baru.

Linux / Mac OS / WSL Launcher:

run.sh
#!/bin/bash # ======================================================== # WA-Bot Pro - Linux / Mac Automated Background Launcher # ======================================================== echo "[*] Menyalakan backend server..." cd backend && npm start & BACKEND_PID=$! sleep 3 echo "[*] Menyalakan frontend server..." cd ../frontend && npm run dev & FRONTEND_PID=$! # Trap untuk mematikan kedua child-process secara bersih saat Ctrl+C ditekan trap "echo -e '\n[*] Menghentikan server...'; kill $BACKEND_PID $FRONTEND_PID 2>/dev/null; exit" SIGINT SIGTERM echo "[SUCCESS] Server aktif di background. Tekan [Ctrl+C] untuk keluar secara bersih." wait

7.1.2 Backend Runtime Roles #

Backend mendukung pemisahan proses berbasis runtime role. Mode npm start tetap menjadi monolith untuk lokal, sedangkan deployment dapat menjalankan API dan worker sebagai proses PM2/systemd terpisah. API-only juga dapat mendelegasikan operasi session inti ke session manager internal memakai WA_BOT_SESSION_MANAGER_URL dan WA_BOT_INTERNAL_TOKEN.

Tabel 7.1.2 -- Command Runtime Role Backend
RoleCommandTanggung Jawab
Monolith lokalnpm startMenjalankan API, restore sesi, campaign worker, dan warmer worker dalam satu proses.
API onlynpm run start:apiMenjalankan Express API tanpa worker inline.
Session managernpm run start:sessionsMemulihkan sesi Baileys tanpa membuka HTTP API.
Campaign workernpm run start:campaign-workerPolling SQLite untuk kampanye PENDING dan mengirim bulk message.
Warmer workernpm run start:warmer-workerPolling SQLite untuk kampanye warmer RUNNING.
Combined workernpm run start:workerMenjalankan session restore, campaign worker, dan warmer worker tanpa HTTP API.
Internal session-manager API saat ini mencakup list/status/init/delete/proxy update dan readiness endpoint. Delegasi fitur socket-heavy lain seperti group grabber, single-message, campaign send, dan warmer send masih perlu diselesaikan sebelum split production benar-benar penuh.

7.2 Topologi Deployment Sistem #

Menggambarkan topologi infrastruktur fisik dari WA-Bot Pro saat dideploy ke server VPS Linux. Reverse proxy Nginx/Caddy menjadi gerbang TLS, menyajikan frontend statis, memforward request /api ke backend private, menjaga admin auth tetap server-side, serta menghubungkan worker, SQLite, sesi Baileys, backup, dan monitoring VPS.

7.3 VPS Deployment Readiness Plan #

Deployment publik hanya boleh dilakukan setelah item P0 pada roadmap SDLC selesai. Baseline admin auth cookie sudah tersedia, tetapi backend tetap tidak boleh dipublikasikan langsung di port 3001; reverse proxy harus menjadi gerbang TLS, static frontend, dan autentikasi.

Tabel 7.3 -- Baseline Arsitektur VPS Production
LayerKeputusan Target
Reverse proxyNginx atau Caddy sebagai TLS termination, static frontend server, dan gateway menuju backend private.
Backend exposureExpress tetap di port private/local; jangan buka 3001 langsung ke internet.
Process managersystemd atau PM2 dengan restart policy, log rotation, environment variable non-repo, dan service user non-root.
Backend runtime rolesGunakan npm run start:api untuk API-only dan npm run start:worker atau worker granular untuk proses background. Gunakan WA_BOT_SESSION_MANAGER_URL untuk delegasi session manager.
FirewallBuka hanya 22, 80, dan 443; batasi SSH dengan key dan fail2ban bila tersedia.
Runtime databackend/database.sqlite dan backend/sessions/ berada di storage terlindungi, bukan di webroot.
BackupBackup terenkripsi terjadwal aktif secara lokal; offsite copy ke storage luar VPS ditunda sampai tujuan storage tersedia.
MonitoringUptime Kuma untuk endpoint HTTP, Netdata/Prometheus/Grafana untuk resource, dan alert untuk disk, process, session, dan campaign.
Checklist kesiapan: admin authentication aktif, CORS hanya domain produksi, secret dikelola environment/service manager, runtime role split dicatat dalam PM2/systemd, session-manager internal API dikonfigurasi, delegasi socket-heavy selesai, migrasi dan restore drill berhasil, monitoring aktif, log rotation berjalan, serta QA penuh dan smoke test deploy tercatat.
Evidence staging 5 Juni 2026: staging sudah menjalankan Caddy domain HTTPS, frontend build, systemd wa-bot-api, systemd wa-bot-worker, secure cookie/CORS, API readiness status=ready, worker readiness status=ready, UFW aktif hanya untuk 22/80/443, systemd backup/restore timers, local healthcheck timer, logrotate, dan HTTP/HTTPS smoke. Status ini belum production-ready sampai provider firewall review, external alert monitoring, manual smoke evidence HTTPS, dan offsite backup saat storage tersedia selesai.

8.1 Rencana Pemeliharaan Sistem Berkelanjutan #

Struktur rencana pemeliharaan sistem dibagi menjadi tiga jenis penanganan utama untuk menjaga kestabilan jangka panjang sistem WhatsApp integration.

Pemeliharaan Preventif (Preventive Maintenance)
Jadwal: Bulanan
Menghapus data riwayat logs di tabel delivery_logs yang usianya melebihi 30 hari untuk mencegah pembengkakan database SQLite (Database Vacuuming). Melakukan audit berkala file kredensial untuk membuang sesi mati yang tidak digunakan.
Pemeliharaan Korektif (Corrective Maintenance)
Jadwal: Ad-Hoc / Ketika Crash
Memantau logs crash dan memperbarui dependensi @whiskeysockets/baileys mengikuti pembaruan protokol API internal Meta. Memecahkan masalah (hotfix) apabila terjadi kegagalan sinkronisasi autologin sesi yang terputus.
Pemeliharaan Perfektif (Perfective Maintenance)
Jadwal: Sesuai Roadmap Fitur
Menambah fungsionalitas pendukung baru seperti integrasi chatbot berbasis AI (OpenAI/Gemini), sistem reporting pengiriman pesan massal berformat PDF otomatis, serta optimasi caching memory Redis.
